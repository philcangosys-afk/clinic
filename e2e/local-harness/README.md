# بيئة الفحص المحلّية — ولماذا يجب أن تُشبه Supabase تمامًا

ملفّات هذا المجلّد تُنفَّذ على قاعدة Postgres محلّية **قبل** ملفّات `migrations`،
لتحاكي ما توفّره منصّة Supabase: مخطّط `auth`، ودالّة `auth.uid()`، ومنح
الصلاحيات للأدوار `anon` و`authenticated`.

## لماذا هذا الملفّ مهمّ

بيئة الفحص التي كانت مستعملة قبل مراجعة 0143 كانت تخالف Supabase في ثلاثة
أمور، وكلٌّ منها كان يُخفي أخطاءً حقيقية:

1. **`auth.users.email` كان `text`** وهو في Supabase `character varying(255)`.
   والترحيل 0062 يعيد بناء عرض التدقيق بنوع `varchar(255)`، فكان يفشل محلّيًا
   وينجح على الإنتاج — فاختلف اسم عمود هويّة المستخدم بين القاعدتين، وبُنيت
   شاشة سجلّ التدقيق على الاسم الخطأ فلم تفتح أصلًا.

2. **`auth.uid()` كانت تقرأ `app.current_user_id`** بينما Supabase تقرؤها من
   `request.jwt.claim.sub`. أي فحص يضبط الهويّة بالطريقة الصحيحة كان يفشل.

3. **الأدوار `anon` و`authenticated` كانت بلا صلاحيات على الجداول.** المنصّة
   تمنحهما كل الصلاحيات وتترك الحماية لسياسات الصفوف (RLS). بدون ذلك تفشل
   الفحوص بـ«permission denied» فتُقرأ كأنها أخطاء في المنتج لا في البيئة —
   والأخطر أنها تُخفي ما يُصلحه `revoke` داخل ترحيل حقيقي.

## الاستعمال

```bash
createdb aud
psql -d aud -v ON_ERROR_STOP=1 -f e2e/local-harness/auth_stub.sql
psql -d aud -v ON_ERROR_STOP=1 -f e2e/local-harness/storage_stub.sql
# ثم ملفّات migrations بالترتيب الرقمي، ثم ملفّات e2e/sql
```

ملاحظة: ترحيل `0132` يزرع بيانات منشأة حقيقية بعينها، فيفشل على قاعدة فارغة —
يُتجاوز في الفحص المحلّي وحده.
