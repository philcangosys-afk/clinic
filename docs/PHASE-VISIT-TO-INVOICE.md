# مرحلة: المواعيد ← الاستقبال ← الزيارة ← الفاتورة

هذا المستند يجمع ما بُني في هذه المرحلة، وما كُشف من أعطال، وقائمة الاختبار
التي تُجرى على النظام الحي بعد تشغيل الهجرات والدفع.

---

## 1) الهجرات — تُشغَّل بهذا الترتيب

| # | الملف | ماذا يفعل |
|---|---|---|
| 0053 | `0053_visit_services.sql` | خدمات الزيارة + منع الفوترة المزدوجة في القاعدة |
| 0054 | `0054_reminder_delivery_pipeline.sql` | خط تسليم تذكيرات المواعيد (محاولات، تراجع أُسّي، إلغاء) |
| 0055 | `0055_reception_transition_fixes.sql` | **إصلاح «بدء الزيارة»** + إجراء `confirm` + إلزام سبب عدم الحضور |
| 0056 | `0056_visit_children_integrity.sql` | صف واحد لكل زيارة لتوابعها + `next_visit_date` |
| 0057 | `0057_visit_orders_billing.sql` | فوترة طلبات المختبر والأشعة والوصفة |

**0055 هو الأهم.** بدونه زر «بدء الزيارة» يفشل دائمًا ولا يمكن اختبار أي شيء
بعده.

## 2) أخطر ما كُشف

### «بدء الزيارة» لم يعمل قط
`app_reception_transition` معرَّفة `returns table (appointment_id uuid, …)`،
وهذا يُنشئ متغيّر PL/pgSQL ضمنيًا بنفس الاسم. وفي نفس الدالة
`on conflict (appointment_id)` — فيصطدم اسم المتغيّر باسم العمود:

```
ERROR: column reference "appointment_id" is ambiguous
```

النتيجة: الضغط على «بدء الزيارة» يفشل دائمًا، فتتوقف الرحلة عند النداء ولا
تُنشأ زيارة ولا يصل الطبيب إلى السجل الطبي. **لا يظهر هذا في مراجعة الشيفرة
لأن الخطأ لا يقع إلا وقت التنفيذ.**

### الطلبات لم تكن مربوطة بالزيارة
`lab_orders.visit_id` و`radiology_orders.visit_id` و`prescriptions.visit_id`
موجودة منذ 0013/0014/0015، وتعليق 0013 نفسه يقول إنها «حتى يظهر الطلب من داخل
شاشة السجل الطبي **مستقبلًا**». لم يكن في الواجهة كلها سطر واحد يكتبها.

### الطلبات لم تكن تُفوتَر
`lab_tests.billing_item_id` و`radiology_exams.billing_item_id` («الربط بكتالوج
الفوترة») لا تُقرأ ولا تُكتب. و`lab_orders.sales_invoice_id`
و`radiology_orders.sales_invoice_id` («يُملأ عند الفوترة») لم يُملآ قط.
و`prescriptions.is_billed` يُقلَّب **يدويًا** بزر في شاشة الصيدلية.

الأثر: الطبيب يطلب تحليلًا وصورة، ويُنفَّذان، ثم لا يرى المحاسب إلا خدمات
الزيارة. **إيراد نُفِّذ ولا يُحصَّل.**

### إعادة حفظ الزيارة كانت تفشل أو تُكرِّر
- التشخيص: مفتاحه `(visit_id, icd10_code_id)` ⇒ `duplicate key` خام **بعد**
  حفظ الزيارة والخدمات فعلًا.
- الفحص المهني: `unique` على `visit_id` منذ 0033 ⇒ نفس الشيء.
- المؤشرات الحيوية ولوحة الأسنان ومخطط الجسم: بلا قيد ⇒ صف جديد لكل حفظ.

### حصّة المريض لا تُعرض
`insurance_share_amount` و`patient_share_amount` تُحسبان في القاعدة (0052) ولا
تُقرآن في أي شاشة، ولم تكونا معرَّفتين في أنواع TypeScript أصلًا. فالمريض
المؤمَّن يستلم إيصالًا يقول «الصافي 500 والمتبقي 500» بينما لا يخصّه إلا حصته.

### نتائج بلا موثِّق
`lab_orders.verified_by` و`radiology_orders.reported_by` لم يُكتبا قط.

### حالات معرَّفة لا يمكن الوصول إليها
`specimen_collected` و`in_progress` لطلب المختبر لهما تسميتان في الشاشة ولا زر
ينقل إليهما، و`specimen_collected_at` لم يُملأ قط.

## 3) قائمة الاختبار على النظام الحي

بعد تشغيل الهجرات والدفع وانتهاء بناء Netlify:

### أ) المواعيد
- [ ] `/appointments` تفتح بلا خطأ `PGRST201` في الطرفية
- [ ] اختيار يوم فيه مواعيد ويوم فارغ
- [ ] البحث بالاسم، برقم الملف، بالجوال
- [ ] تصفية بالحالة
- [ ] إنشاء موعد بكل الحقول
- [ ] تأكيد / إعادة جدولة / إلغاء بسبب
- [ ] الانتقال إلى ملف المريض وإلى الاستقبال

### ب) الاستقبال
- [ ] تأكيد ← وصول ← تسجيل ← نداء ← **بدء الزيارة** ← إنهاء
- [ ] رقم الدور يُمنح مرة واحدة (إعادة تسجيل الوصول لا تُقدّم المريض)
- [ ] النداء قبل الوصول مرفوض
- [ ] القفز من «مجدول» إلى «إنهاء» مرفوض
- [ ] عدم الحضور بلا سبب مرفوض
- [ ] «بدء الزيارة» مرتين لا يُنشئ زيارتين

### ج) مريض بلا موعد وقائمة الانتظار
- [ ] `/reception` — إضافة مريض بلا موعد بأولوية عاجلة
- [ ] `/waitlist` — تحويل طلب انتظار إلى موعد؛ التحويل مرتين مرفوض

### د) الزيارة
- [ ] الشكوى، الفحص الديناميكي، المؤشرات الحيوية، التشخيص ICD-10
- [ ] الخدمات المنفَّذة
- [ ] **الطلبات والوصفة**: تحليل + أشعة + دواء بجرعة وتكرار ومدة
- [ ] تاريخ المتابعة
- [ ] **إعادة الحفظ لا تُخطئ ولا تُكرِّر** (احفظ الزيارة مرتين وتحقّق)
- [ ] ملف المريض ← الزيارات ← السهم يعرض كل ما سبق

### هـ) المختبر والأشعة
- [ ] كتالوج الفحوص: ربط فحص بصنف فوترة (عمود «صنف الفوترة»)
- [ ] الطلب الصادر من الزيارة يظهر في شاشة المختبر
- [ ] تسجيل سحب العيّنة ← بدء التنفيذ ← إدخال النتائج ← توثيق
- [ ] تقرير الأشعة يُوثَّق ويُسجَّل كاتبه

### و) الفاتورة
- [ ] صندوق «الخدمات المنفَّذة في الزيارة»
- [ ] صندوق **«طلبات الزيارة غير المفوترة»**
- [ ] إضافة طلب كامل ← إصدار ← الطلب يختفي من الصندوق ويظهر «مفوتر» في الزيارة
- [ ] محاولة فوترته ثانيةً من نافذة أخرى ⇒ رفض بلا فاتورة يتيمة
- [ ] فاتورة تأمين: الإيصال يعرض حصة الشركة وحصة المريض
- [ ] فحص غير مربوط بصنف: تنبيه صريح لا اختفاء صامت

### ز) الرحلة الكاملة بأربعة أدوار
مستقبِل يحجز ويستقبل ← طبيب يفحص ويطلب ويصف ← فنّي يُدخل النتائج ← محاسب
يُصدر الفاتورة شاملةً الخدمات والطلبات ← مدير يرى كل ذلك في ملف المريض.

## 4) ما زال مهجورًا (يحتاج قرارك)

| العمود | ماذا يعني تركه |
|---|---|
| `sales_invoices.zatca_qr` | لا رمز QR لفاتورة زاتكا — بند امتثال سعودي |
| `applied_offer_id` / `offer_percent` | العروض تُعرَّف ولا تُربط بأي فاتورة، فلا يُعرف أثرها |
| `prescription_items.is_substitutable` | الصيدلي لا يُخبَر بجواز الاستبدال بمكافئ |
| `lab_order_items.unit_override` | لا يمكن تجاوز وحدة القياس لفحص بعينه |
